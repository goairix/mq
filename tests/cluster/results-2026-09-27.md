# v2 集群验证记录（2026-09-27）

环境：Apple M5、16 GiB 主机内存，Docker Desktop 8 vCPU / 约 11.7 GiB 内存，Go 1.25.8、Docker 29.8.0。所有 broker 容器位于同一 Docker 主机。通过 `bash tests/cluster/run.sh all` 完成故障测试，并分别运行 `bench` 模式；命令和拓扑见 [README.md](README.md)。

## 故障恢复

| 场景 | 本机结果 |
| --- | --- |
| Kafka 4.0.2、4.1.2 三节点，杀分区 leader | 通过；故障前后确认的消息 ID 均被消费 |
| RabbitMQ 3.13.3 三节点 quorum，杀普通队列 leader | 通过；重连存活节点后继续发布和消费 |
| RabbitMQ 3.13.3 三节点 quorum，杀 TTL/DLX 延时桶 leader | 通过；杀节点前确认任务仍在目标桶，切换后两个任务均投递 |
| Redis 7.2、8.0 三主三从，杀 slot 主节点 | 普通 Stream 和延时任务均通过；先确认副本已有记录，再注入故障 |
| Redis Sentinel 7.2、8.0，一主两从、三个 Sentinel，杀数据主节点 | 普通 Stream 和延时任务均通过；先确认两个副本已有记录，三个 Sentinel 选出同一新主，原 `FailoverClient` 继续工作 |

Kafka、RabbitMQ、Redis 的单节点反例均按预期拒绝所需集群拓扑。Redis 异步复制仍可能丢失**尚未复制**的已确认写入，此测试没有证明零丢失。

## 确认发布基准

命令：`bash tests/cluster/run.sh bench`，默认 `-benchtime=2s -count=1`。每批 256 条、每条 1 KiB；以下为本机单次探索性采样。Kafka 已在计时前预热连接。数值为有效载荷 MB/s，同一行只比较同一个 backend 的 adapter 与直接客户端。

| 集群 | adapter MB/s | 直接客户端 MB/s | 说明 |
| --- | ---: | ---: | --- |
| Kafka 4.0.2 | 275.78 | 279.81 | 单分区，RF3，`min.insync.replicas=2`，`acks=all` |
| Kafka 4.1.2 | 294.43 | 281.84 | 同上 |
| RabbitMQ 3.13.3 | 29.60 | 26.77 | 三副本持久化 quorum，publisher confirms |
| Redis 7.2 | 28.02 | 26.62 | 六节点，AOF `appendfsync always`，交替配对采样 |
| Redis 8.0 | 24.71 | 24.60 | 同上 |
| Redis Sentinel 7.2 | 14.86 | 13.68 | 一主两从、三 Sentinel，副本连接健康后采样，AOF `appendfsync always`，交替配对采样 |
| Redis Sentinel 8.0 | 15.72 | 15.94 | 同上 |

这些短采样只覆盖一个 Kafka 分区、一个 RabbitMQ quorum 队列或一个 Redis Stream key，会受 Docker 资源、磁盘同步、缓存和测试顺序影响，不能据此给出集群聚合容量上限或生产环境 SLO。没有运行端到端消费吞吐、积压追赶、长时间稳态负载或故障同时施加持续负载的测试。评估业务容量时应按真实消息大小、分区与消费者并发、处理耗时和下游写入能力重复测量。
